# InnoDB 더블라이트 버퍼: redo log가 있는데도 왜 페이지를 두 번 쓰는가 (torn page 방지)

> **Primary source:** MySQL 8.0 Reference Manual §17.6.4 "Doublewrite Buffer", §17.11.1 "InnoDB Disk I/O" / InnoDB 소스 `storage/innobase/buf/buf0dblwr.cc`
> **Secondary:** MySQL 8.0.20 Release Notes (dblwr 파일 분리) / Jeremy Cole "InnoDB doublewrite" 분석 글
> **Date:** 2026-07-27
> **Status:** draft

## 왜 봤나

- "redo log로 크래시 복구가 되는데 왜 더블라이트라는 게 또 필요하지? I/O만 두 배 아닌가"라는 의문이 계속 남아 있었다.
- 막연히 "더블라이트 = 쓰기 두 배 = 성능 반토막"이라고 알고 있었는데, 왜 켜두는 게 기본값인지 인과를 끝까지 따라가 본 적이 없었다.

## 핵심 한 문장

> 더블라이트 버퍼는 **로그가 아니라** "찢어진 페이지(torn page)"를 복구하기 위한 **온전한 페이지 사본**이다 — redo log는 *일관된 base 페이지 위에* delta를 얹는 구조라, 페이지 자체가 물리적으로 반쯤 쓰이면 redo만으로는 절대 되살릴 수 없기 때문이다.

## 내부 동작

### 1. torn page는 왜 생기나 — 원자성 단위의 불일치

InnoDB 페이지는 기본 16KB다. 그런데 그 16KB를 디스크에 내려보내는 하위 계층(OS page cache, 파일시스템, 블록 디바이스)의 **원자적 쓰기 단위는 보통 4KB(또는 512B 섹터)**다. 즉 16KB 페이지 하나를 flush하면 실제로는 4KB짜리 물리 쓰기 여러 개로 쪼개진다.

이 여러 개의 물리 쓰기 도중에 전원이 나가거나 커널이 패닉하면, 페이지의 앞 8KB는 새 내용, 뒤 8KB는 옛 내용인 **반쯤 쓰인 페이지**가 디스크에 남는다. 이게 torn page(partial page write)다. InnoDB 버그가 아니라, **페이지 크기 > 디바이스 원자 쓰기 단위**라는 구조에서 필연적으로 생긴다.

### 2. redo log가 이걸 못 고치는 이유

InnoDB의 redo는 순수 물리 로그가 아니라 **physiological**(페이지 단위 물리 + 페이지 내부는 논리) 로그다. 복구 시 redo 레코드는 "이 페이지의 이 오프셋에 이 연산을 적용하라"는 식으로 **디스크에 있는 기존 페이지를 읽어와 그 위에 재적용**된다.

여기서 전제가 깨진다: redo 적용은 **base 페이지가 내부적으로 일관됨**을 가정한다. 페이지 헤더의 레코드 디렉터리, 슬롯, 다음 레코드 포인터가 성해야 그 위에 delta를 얹을 수 있다. 그런데 torn page는 헤더 절반과 데이터 절반이 서로 다른 버전이라 **구조 자체가 깨진 상태**다. 이런 페이지엔 redo를 얹을 base가 없다. 로그는 "무엇을 바꿨는가"만 알지 "온전한 페이지 전체 이미지"를 갖고 있지 않기 때문이다.

→ 그래서 **온전한 페이지 사본**을 따로 둬야 한다. 그게 더블라이트다.

### 3. 쓰기 순서 — 왜 "두 번"이 안전을 만드는가

더티 페이지를 flush할 때 InnoDB는 **최종 위치(데이터 파일의 흩어진 곳)에 바로 쓰지 않는다**. 순서가 핵심이다.

```
flush 대상 더티 페이지 배치 (최대 수십~128개)
        │
        ▼
① 더블라이트 영역(연속된 공간)에 배치 전체를 sequential write
        │
        ▼
② fsync  ← 여기까지 끝나야 ③ 시작 (배리어)
        │
        ▼
③ 각 페이지를 데이터 파일의 진짜 최종 위치(random)에 write
        │
        ▼
④ (주기적으로) 최종 위치 fsync
```

이 순서 덕분에 크래시가 **어느 지점에서 나든** 둘 중 하나가 보장된다:

- ③ 도중 최종 위치 페이지가 찢어졌다 → 더블라이트 영역엔 ①에서 fsync까지 끝낸 **온전한 사본**이 있다.
- ① 도중 더블라이트 영역이 찢어졌다 → 최종 위치의 페이지는 **아직 손 안 댄 옛 온전한 버전**이다.

즉 "온전한 원본"과 "온전한 사본"이 동시에 깨질 창(window)이 없다. 이것이 배리어(②)가 사는 이유다.

### 4. 복구 시 판정 — torn page를 어떻게 알아채나

복구할 때 InnoDB는 각 페이지의 **체크섬**과 LSN 정합성을 검사한다. 전통적으로 페이지 헤더(`FIL_PAGE_LSN`)와 페이지 트레일러(끝 8바이트, LSN 하위 32비트)가 일치해야 하고, 페이지 체크섬이 맞아야 한다. 앞뒤 LSN이 어긋나거나 체크섬 불일치면 = **쓰기가 중간에 끊긴 torn page**.

이때 더블라이트 영역을 훑어 해당 page id의 사본을 찾고, 그 사본의 체크섬이 정상이면 **최종 위치에 복원**한다. 그 다음에야 redo를 정상 재적용한다. 더블라이트는 "복구 진입점에서 base 페이지를 온전하게 만들어 주는" 전처리 단계인 셈이다.

### 5. 왜 I/O가 두 배가 아닌가 — 비용 구조

데이터 *양*은 대략 두 배가 맞다(같은 페이지를 dblwr + 최종에 한 번씩). 하지만 체감 비용은 2배에 한참 못 미친다:

- 더블라이트 쓰기는 **연속 공간에 대한 sequential write**다. 최종 flush는 데이터 파일 곳곳으로 흩어지는 random write인데, sequential 쪽은 디스크에 훨씬 싸다.
- 여러 페이지(최대 수십~128개)를 **한 배치로 모아 single fsync** 뒤로 보낸다. fsync 횟수가 페이지 수만큼 늘지 않는다.

레이아웃: 8.0.20 이전에는 시스템 테이블스페이스 안에 **두 블록 × 각 64페이지 = 128페이지(16KB 기준 2MB)** 형태였다. 8.0.20+부터는 `#ib_16384_0.dblwr` 같은 **별도 파일**로 분리되고 `innodb_doublewrite_files`, `innodb_doublewrite_pages`로 조정 가능하다(공식 문서 기준). 크기가 작아도 되는 이유: 더블라이트는 로그처럼 누적 보관하는 게 아니라 **매 배치마다 덮어쓰는 스크래치 공간**이라, 복구에 필요한 건 "가장 최근에 안전하게 사본을 떠 둔 배치"뿐이기 때문이다.

### 6. 끌 수 있는 경우

디바이스가 **16KB 원자적 쓰기를 하드웨어로 보장**하면(일부 Fusion-io/NVMe, atomic write 지원 파일시스템) torn page가 원천적으로 안 생기므로 `innodb_doublewrite=OFF`로 꺼서 쓰기 증폭을 없앨 수 있다. 즉 더블라이트는 "디바이스가 페이지 단위 원자성을 안 주니 소프트웨어로 흉내 낸다"는 성격이다.

## 검증

출처(레퍼런스 매뉴얼)와 소스 흐름을 따라가며 순서 보장을 확인했다. 핵심은 "한쪽이 깨질 때 다른 쪽은 온전"이라는 불변식이다. 상태를 표로 정리하면:

```
크래시 시점        더블라이트 영역        최종 위치           복구 동작
─────────────────────────────────────────────────────────────────────
① 쓰기 중 크래시    torn(무시 가능)        옛 온전 버전         최종 그대로 + redo 재적용
② fsync 후, ③ 전    온전 사본 존재         옛 온전 버전         (아직 안 씀) 그대로
③ 쓰기 중 크래시    온전 사본 존재         torn                dblwr 사본으로 복원 후 redo
③ 완료 후          (다음 배치가 덮어씀)    새 온전 버전         정상
```

②·③ 어느 행에서도 "복원에 쓸 온전한 이미지"가 항상 최소 하나 존재한다 — 이 불변식이 성립하는 이유는 순서 ①→②(fsync 배리어)→③ 때문이고, fsync가 빠지면 ①의 사본이 실제로 디스크에 도달했다는 보장이 없어져 불변식이 깨진다.

의사 흐름(복구 초입):

```text
for each page P referenced by redo before applying:
    if checksum(P_on_disk) is valid and head_LSN == tail_LSN:
        base = P_on_disk                 # 온전 → 그대로
    else:                                # torn 감지
        copy = find_in_doublewrite(page_id(P))
        if copy and checksum(copy) valid:
            write copy -> P_on_disk       # 사본으로 복원
            base = copy
        # (사본도 깨졌다면 그건 ① 단계 크래시 = 최종은 원래 온전)
apply redo records on top of base
```

## 잘못 알고 있던 것

- **"redo log가 크래시를 다 막아주니 더블라이트는 중복이다"** — 아니다. 둘은 **직교하는 계층**이다. redo는 *커밋됐지만 아직 flush 안 된 논리적 변경*을 되살리고, 더블라이트는 *페이지의 물리적 온전성*을 지킨다. redo는 온전한 base 페이지를 **전제**로 하므로, base가 torn이면 redo부터 적용할 대상이 없다. 더블라이트가 그 base를 복구해 주어야 비로소 redo가 의미를 가진다.
- **"페이지를 두 번 쓰니 쓰기 성능이 반토막"** — 데이터 양은 2배지만 더블라이트 쪽은 sequential + 배치 single-fsync라 실제 오버헤드는 스토리지에 따라 대개 한 자릿수 %대다. random 최종 flush가 지배적이라 sequential 추가분은 상대적으로 저렴하다.
- **"torn page는 디스크/InnoDB 결함"** — 결함이 아니라 페이지 크기(16KB)가 디바이스 원자 쓰기 단위(4KB/512B)보다 크다는 구조적 사실의 귀결이다. 그래서 원자 쓰기를 하드웨어가 보장하면 더블라이트를 꺼도 안전하다.

## 더 파고들 만한 것

- 더블라이트 batch flush와 LRU flush / adaptive flushing의 상호작용, page cleaner 스레드 경로.
- PostgreSQL의 동일 문제 해법인 **full_page_writes**(체크포인트 후 첫 수정 시 WAL에 페이지 전체 이미지 기록) 와의 설계 비교 — 로그에 넣느냐(PG) vs 별도 스크래치 영역이냐(InnoDB).
