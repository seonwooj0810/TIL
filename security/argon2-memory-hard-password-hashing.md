# Argon2: 메모리를 채워야만 계산되게 만들어 GPU 병렬 크래킹을 무력화하는 법

> **Primary source:** RFC 9106 (Argon2 Memory-Hard Function for Password Hashing and Proof-of-Work) §3~§4
> **Secondary:** PHC(Password Hashing Competition) 2015 선정 근거, Spring Security `Argon2PasswordEncoder` docs
> **Date:** 2026-07-25
> **Status:** draft

## 왜 봤나

- 비밀번호 저장에 bcrypt 대신 Argon2를 권장한다는 말은 자주 듣는데, "왜 더 안전한가"를 "반복 횟수를 더 돌려서"라고만 알고 있었다. 그건 틀린 요약이었다.
- Argon2의 방어력 핵심은 시간(iteration)이 아니라 **메모리**라는 점, 그리고 그 메모리 강제가 하드웨어 수준에서 무엇을 막는지 끝까지 따라가 보고 싶었다.

## 핵심 한 문장

> Argon2는 해시 한 번을 계산하려면 수십~수백 MiB 메모리를 실제로 채우고 무작위로 되읽게 강제해서, 빠른 연산 코어는 많아도 **빠른 메모리는 적은** GPU·ASIC의 병렬 크래킹 이점을 구조적으로 제거하는 memory-hard 함수다.

## 내부 동작

### 파라미터

RFC 9106 기준 입력: 비밀번호 `P`, salt `S`(권장 16B), 병렬도 `p`(lanes), 메모리 `m`(KiB), 반복 `t`(passes), 태그 길이 `T`, 버전 `v=0x13`(=19, v1.3), 선택적 비밀키 `K`·부가데이터 `X`. 변종 `y`: Argon2d=0, Argon2i=1, Argon2id=2.

### 메모리 레이아웃 — 1024바이트 블록의 행렬

메모리는 **1024바이트 블록** 단위로 잡힌다. 총 블록 수는 `m' = 4·p·floor(m/(4p))`로 4p의 배수로 내림 정렬되고, 이를 `p`개 lane(행) × `q = m'/p`개 column(열)의 행렬 `B[i][j]`로 본다. 각 lane은 다시 **4개 slice**로 세로 분할되며, 이 slice 경계가 병렬 lane 간 동기화 배리어 역할을 한다.

```
        col 0 ....... slice0 | slice1 | slice2 | slice3 ....... col q-1
lane 0  [B00][B01] ...........................................[B0,q-1]
lane 1  [B10][B11] ...........................................[B1,q-1]
...                (lane끼리는 slice 끝에서만 서로의 블록을 참조 가능)
lane p-1[.. ]                                                 [Bp-1,q-1]
                                                                 |
     최종 태그 = H'( B[0][q-1] XOR B[1][q-1] XOR ... XOR B[p-1][q-1] )
```

### 초기 블록

`H0 = BLAKE2b(p, T, m, t, v, y, len(P)‖P, len(S)‖S, len(K)‖K, len(X)‖X)` (64B). 각 lane의 앞 두 블록만 이 H0에서 직접 나온다:

```
B[i][0] = H'(H0 ‖ LE32(0) ‖ LE32(i))
B[i][1] = H'(H0 ‖ LE32(1) ‖ LE32(i))
```

`H'`는 BLAKE2b를 이어붙여 임의 길이(여기선 1024B)를 뽑는 가변길이 해시다.

### 채우기 — 압축함수 G와 참조 인덱싱

이후 모든 블록은 두 블록을 섞어 만든다:

```
B[i][j] = G( B[i][j-1],  B[i'][j'] )      // t>1인 pass에선 기존 B[i][j]와 XOR해 덮어씀
```

- `B[i][j-1]`: 같은 lane의 직전 블록.
- `B[i'][j']`: **참조 블록** — 인덱싱 함수가 정한 (지금까지 계산된) 임의 위치. 이 "무작위 되읽기"가 memory-hardness의 심장이다.

압축함수 `G(X,Y)`: 먼저 `R = X XOR Y` (1024B를 8×8의 16B 워드 행렬로 봄). BLAKE2b 라운드 함수 `P`를 **행 방향 8번 → 열 방향 8번** 적용해 확산시킨 결과 `Z`를 얻고, 출력은 `Z XOR R`. 즉 전체 1024B가 서로에게 영향을 주도록 뒤섞는다.

### 변종이 갈리는 지점: 참조 인덱스를 어떻게 뽑나

참조 위치 `(i',j')`는 두 값 `J1,J2`에서 나온다. 이걸 **어디서 얻느냐**가 d/i/id를 가른다.

| 변종 | J1,J2 출처 | 성질 |
|---|---|---|
| Argon2d | 직전 블록 `B[i][j-1]`의 첫 64비트 (**데이터 의존**) | 접근 패턴이 비밀에 의존 → 캐시 타이밍 사이드채널 취약, 대신 TMTO 저항 최대 |
| Argon2i | `G`를 카운터 모드로 돌려 생성 (**데이터 독립**) | 접근 패턴이 입력과 무관 → 사이드채널 안전, 대신 트레이드오프 공격 여지 |
| Argon2id | 첫 pass의 전반 절반은 i처럼, 이후는 d처럼 | 둘의 절충. **RFC 9106 기본 권장** |

`J2`는 참조할 lane을, `J1`은 그 lane 안에서 참조 area 내 상대 위치를 정한다(비균등 매핑으로 최근 블록에 더 몰리게). 참조 area 규칙: 이미 완성된 slice의 블록 + 현재 segment에서 이번 것 직전까지 계산된 블록. 다른 lane은 **직전 slice까지만** 참조 가능 — 이 제약 덕에 lane들을 slice 단위로 병렬 계산할 수 있다.

### 마무리

`t`번의 pass를 다 돌면 마지막 열의 모든 lane 블록을 XOR한 `C`를 만들고, `Tag = H'(C, T)`. 인코딩 문자열은 `$argon2id$v=19$m=65536,t=3,p=4$<b64salt>$<b64hash>` 형태로, 파라미터가 해시에 함께 박혀 검증 시 그대로 복원된다.

### 왜 이게 GPU/ASIC을 막나

공격자가 초당 수십억 해시를 뽑으려면 후보 비번마다 **독립적으로 `m` KiB 메모리**를 잡고 무작위 접근해야 한다. GPU는 산술 코어는 수천 개지만 코어당 붙는 빠른 메모리(레지스터/공유메모리)는 작다. m을 64MiB로 잡으면 동시 실행 가능한 해시 수가 메모리 대역폭·용량에 묶여 급감한다. bcrypt(~4KiB 고정)나 PBKDF2(메모리 거의 0)가 GPU에 잘 뚫리는 이유가 바로 이 메모리 비용의 부재다.

"그럼 메모리를 안 쓰고 그때그때 다시 계산하면 되지 않나"가 자연스러운 반격인데(time-memory tradeoff, TMTO), 참조 블록이 **이전에 계산된 임의 위치**를 가리키고 각 블록이 압축함수로 전부 뒤섞여 있어, 한 블록을 버렸다가 다시 만들려면 그 블록이 참조한 블록, 또 그게 참조한 블록…으로 재계산이 연쇄 폭발한다. RFC 9106은 메모리를 절반으로 줄이면 계산량이 큰 상수배로 뛰도록(저장을 포기하는 순간 시간비용이 감당 못 하게) 설계됐다고 기술한다. Argon2i가 데이터 독립이라 사이드채널엔 강해도 TMTO 여지가 상대적으로 크고, id/d가 데이터 의존 접근으로 이 재계산 저항을 더 높이는 것이 변종 선택의 실질적 트레이드오프다.

### pass가 2회 이상일 때(t>1)

두 번째 pass부터는 새로 계산한 블록을 **덮어쓰지 않고** 기존 값과 XOR해 갱신한다(`B[i][j] = old XOR G(...)`, v1.3부터). 덕분에 pass를 늘려도 메모리 사용량은 그대로 `m`을 유지하면서 각 블록에 더 많은 입력 이력이 누적된다 — `t`가 "메모리 재사용 횟수"이자 시간비용 손잡이인 이유다.

## 검증

RFC 9106 §3.2의 블록 인덱싱과 Spring Security 기본값으로 흐름을 따라가 봤다.

```java
// Spring Security 6 — Argon2id, m=16MiB, t=3, p=1(예)
Argon2PasswordEncoder enc =
    new Argon2PasswordEncoder(16, 32, 1, 1 << 14, 3); // saltLen,hashLen,p,m(KiB),t
String h = enc.encode("s3cr3t");
// -> $argon2id$v=19$m=16384,t=3,p=1$<salt>$<hash>
//    문자열에 파라미터가 박혀 있어 matches()가 같은 m/t/p로 재계산해 비교
enc.matches("s3cr3t", h); // true
```

- `m=16384`(KiB)는 해시 1회에 16MiB를 실제로 채운다는 뜻 → 검증 서버도 그만큼 쓴다(로그인 폭주 시 DoS 고려 지점).
- 같은 비번이라도 salt가 매번 달라 출력이 달라진다(아래 오해 참고).

## 잘못 알고 있던 것

- **"반복 횟수 t를 키우는 게 핵심 방어다."** 아니다. Argon2의 차별점은 memory-hardness, 즉 파라미터 `m`이다. `t`는 시간비용을 선형으로 올리는 보조 손잡이일 뿐, GPU/ASIC의 병렬 이점을 무너뜨리는 건 큰 `m`과 무작위 메모리 접근이다. RFC 권장값도 메모리를 크게(예: 64MiB~2GiB) 잡는 쪽에 무게가 있다.
- **"salt가 해시를 느리게 한다."** salt는 속도와 무관하다. salt는 레인보우 테이블 무력화와 "같은 비번→같은 해시" 방지용이고, 느리게 만드는 비용은 오직 `m·t·p`다. 둘을 뭉뚱그리면 salt를 늘려 보안을 높이려는 헛수고를 하게 된다.
- **"Argon2d가 최신·최강이라 그걸 쓰면 된다."** 실무 기본은 Argon2id다. Argon2d는 데이터 의존 접근이라 공유 호스트에서 캐시 타이밍 사이드채널에 노출될 수 있고, Argon2i는 사이드채널엔 강하지만 트레이드오프 공격 여지가 있다. id가 둘을 절충해 RFC 9106이 기본으로 권장한다.

## 더 파고들 만한 것

- bcrypt의 Blowfish 키 스케줄(EksBlowfish)과 cost factor가 왜 메모리는 안 늘리고 시간만 늦추는가 — Argon2와의 정량 비교.
- scrypt의 ROMix/BlockMix와 Argon2 memory-hardness 정의(TMTO 저항)의 차이.
