# HOTP/TOTP: HMAC 동적 절단(Dynamic Truncation)이 6자리 OTP를 만드는 법

> **Primary source:** RFC 4226 (HOTP) §5 (Algorithm), §5.3 (Dynamic Truncation), §7.2–§7.4 (동기화·throttling), Appendix D (Test Vectors) / RFC 6238 (TOTP) §4 (Algorithm), §5.2, §6 (Resynchronization)
> **Secondary:** RFC 2104 (HMAC)
> **Date:** 2026-08-12
> **Status:** draft

## 왜 봤나

- OAuth 2.0 / JWT / PKCE를 정리하면서 "2단계 인증 앱(Google Authenticator 등)이 표시하는 6자리 숫자는 어떻게 만들어지나"를 한 번도 안 짚었다.
- "HMAC 결과를 그냥 앞에서 몇 바이트 잘라 숫자로 바꾸는 것"이라고 생각했는데, 실제로는 **자르는 위치 자체가 매번 달라지는 동적 절단**이라는 걸 확인하고 싶었다.

## 핵심 한 문장

> HOTP는 `HMAC-SHA-1(비밀키, 카운터)`의 20바이트 출력에서 **출력값 자신의 마지막 니블이 가리키는 위치**에서 4바이트를 뽑아(Dynamic Truncation), 최상위 비트를 마스킹해 31비트 양수로 만든 뒤 `mod 10^Digit`으로 6자리 십진수를 얻는 알고리즘이고, TOTP는 그 카운터를 "현재 시각을 30초 단위로 나눈 정수"로 바꿔 끼운 것뿐이다.

## 내부 동작

### 1. HOTP 정의 (§5)

```
HOTP(K, C) = Truncate( HMAC-SHA-1(K, C) )
```

- `K`: 클라이언트·서버가 공유하는 비밀키(보통 등록 시 QR 코드로 전달되는 base32 시드).
- `C`: 8바이트 big-endian 카운터(HOTP는 이벤트 카운터, TOTP는 시간에서 파생).
- `HMAC-SHA-1(K, C)`: RFC 2104 HMAC을 SHA-1로 인스턴스화한 20바이트(160비트) 출력.
- `Truncate`: 그 20바이트를 6~8자리 십진수로 압축하는 §5.3의 Dynamic Truncation 함수.

전체 파이프라인:

```
K, C(8B) ──HMAC-SHA1──▶ String[0..19] (20바이트)
                              │
                    §5.3 Dynamic Truncation
                              │
                    offset = String[19] & 0x0F   (0~15)
                              │
              P = String[offset..offset+3]  (4바이트, big-endian 정수)
                              │
                    Snum = P & 0x7FFFFFFF    (최상위 비트 마스킹 → 31비트)
                              │
                    HOTP값 = Snum mod 10^Digit  (Digit=6이면 6자리, 앞자리 0 유지)
```

### 2. Dynamic Truncation이 "동적"인 이유 (§5.3)

고정 위치(예: 항상 첫 4바이트)를 자르는 게 아니라, **오프셋 자체를 HMAC 출력의 마지막 바이트 하위 4비트로 결정**한다. 20바이트 배열에서 4바이트를 뽑아야 하므로 오프셋 범위는 정확히 0~15(20−4)로 딱 맞아떨어진다.

이렇게 하는 이유는 두 가지다.

- **입력마다 절단 위치가 달라져 예측 가능한 고정 패턴이 남지 않는다.** 공격자가 "HOTP는 항상 바이트 0~3만 본다"는 걸 알아도 소용없다 — 위치가 매 카운터 값마다 HMAC 출력에 따라 바뀐다.
- **HMAC 출력 전체(20바이트)가 최종 값에 영향을 준다.** 마지막 바이트가 오프셋을 정하고, 그 오프셋의 4바이트가 값을 정하므로, 20바이트 중 최소 5바이트(오프셋 결정용 1 + 추출된 4)가 항상 관여한다.

### 3. 31비트 마스킹 — 왜 32비트 그대로 안 쓰나

4바이트를 그대로 정수로 읽으면 플랫폼에 따라 최상위 비트를 부호 비트로 해석하는 언어(Java의 `int`, C의 `signed int` 등)에서는 음수가 나올 수 있다. RFC는 `P`의 최상위 바이트를 `0x7f`로 마스킹해 최상위 비트를 강제로 0으로 만들고 나머지 31비트만 쓴다. 이렇게 하면 결과가 항상 0 이상의 정수로 해석되므로, 구현 언어나 아키텍처의 정수 부호 처리 차이와 무관하게 **모든 구현이 같은 십진수를 계산**한다. RFC 문구로는 "masking out the signed bit removes all ambiguity" — 부호 비트를 지우는 게 목적이라는 뜻이다.

### 4. mod 10^Digit — 자릿수 절단이 보안을 깎는가

31비트 정수(최대 약 21억)를 `10^6`으로 나눈 나머지를 취하면 000000~999999 범위의 6자리 숫자가 나온다. 이 모듈로 연산 자체는 정보를 버리는 것이지만, 각 6자리 값을 만들어내는 31비트 입력이 여러 개씩 존재하므로 값 자체의 예측 난이도는 여전히 원래 HMAC-SHA-1의 계산 불가능성에 의존한다 — 공격자가 값을 역산하려면 여전히 SHA-1을 뒤집어야 한다.

### 5. TOTP = 카운터를 시간으로 바꾼 HOTP (RFC 6238 §4)

```
T = floor( (현재 Unix 시각 - T0) / X )
TOTP(K) = HOTP(K, T)
```

- `X`: 시간 스텝, 기본 30초.
- `T0`: 기준 시각, 기본 0(Unix epoch).
- `T`는 8바이트 big-endian으로 변환해 그대로 HOTP의 카운터 `C` 자리에 들어간다 — **알고리즘 자체는 바뀌지 않고 카운터의 출처만 바뀐다.**

예: Unix 시각 59초 → T=1, 60초 → T=2(§4.2 예시). 즉 각 30초 구간 내에서는 같은 T값을 쓰므로 같은 6자리 코드가 유지되고, 구간이 바뀌면 코드가 바뀐다.

### 6. 동기화 문제와 대응

- **HOTP(이벤트 카운터)**: 클라이언트가 버튼을 눌렀는데 서버에 전달되지 않는 경우가 생기면 클라이언트 카운터가 서버보다 앞서게 된다. §7.4는 서버에 look-ahead 파라미터 `s`를 두어, 서버가 현재 카운터부터 `s`개 앞선 값까지 미리 계산해 비교하도록 권장한다. 일치를 찾으면 서버 카운터를 그 지점으로 전진시킨다.
- **TOTP(시간 카운터)**: 클라이언트·서버 시계가 어긋나면 값이 안 맞을 수 있다. §6은 검증기가 **뒤쪽으로 제한된 개수의 시간 스텝**을 허용하도록 권장한다 — 예를 들어 기본 30초 스텝에서 뒤로 2스텝까지 허용하면 최대 드리프트는 약 89초까지 흡수된다. §5.2는 이 창을 넓힐수록 사용성은 좋아지지만 **브루트포스 공격에 노출되는 시도 횟수도 늘어난다**는 트레이드오프를 명시한다 — 기본 30초 스텝은 이 균형점으로 권장된 값이다.
- **재사용/무차별 대입 방지(HOTP §7.2, §7.3)**: 서버 카운터는 **검증에 성공했을 때만** 전진한다. 실패한 시도는 카운터를 움직이지 않는다. 그리고 throttling 파라미터 `T`(최대 시도 횟수)를 두어 로그인 세션을 넘나드는 병렬 시도까지 포함해 제한하도록 권장한다.

## 검증

RFC 4226 Appendix D는 비밀키를 ASCII 문자열 `"12345678901234567890"`(20바이트)으로 고정하고, 카운터 0~9에 대한 HMAC-SHA-1 값과 최종 6자리 HOTP 값을 표로 제공한다. 아래 스니펫을 그대로 돌려보면 이 값과 정확히 일치하는지 재현할 수 있다.

```java
import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;
import java.nio.ByteBuffer;

static int hotp(byte[] key, long counter, int digits) throws Exception {
    byte[] c = ByteBuffer.allocate(8).putLong(counter).array();      // 8바이트 big-endian 카운터
    Mac mac = Mac.getInstance("HmacSHA1");
    mac.init(new SecretKeySpec(key, "HmacSHA1"));
    byte[] hash = mac.doFinal(c);                                    // 20바이트 HMAC-SHA-1 출력

    int offset = hash[19] & 0x0F;                                    // §5.3 동적 오프셋 (0~15)
    int p = ((hash[offset] & 0x7f) << 24)                             // 최상위 바이트만 0x7f 마스킹
          | ((hash[offset + 1] & 0xff) << 16)
          | ((hash[offset + 2] & 0xff) << 8)
          |  (hash[offset + 3] & 0xff);
    int mod = (int) Math.pow(10, digits);
    return p % mod;                                                  // 6자리면 mod=1_000_000
}

// hotp("12345678901234567890".getBytes(US_ASCII), 0, 6) == 755224
// hotp("12345678901234567890".getBytes(US_ASCII), 1, 6) == 287082
```

확인 포인트:

- `counter=0`일 때 결과가 `755224`, `counter=1`일 때 `287082`가 나오면 Dynamic Truncation 구현이 RFC와 일치한다(Appendix D 표의 처음 두 행).
- `offset` 값을 출력해보면 카운터마다 다른 값(0~15 사이에서 산발적으로)이 나오는 것을 볼 수 있다 — "항상 같은 위치를 자른다"는 가정이 틀렸음을 직접 확인할 수 있는 지점.
- TOTP를 확인하려면 위 함수에 `counter` 대신 `Instant.now().getEpochSecond() / 30`을 넣고, `date +%s` 셸 명령으로 얻은 현재 Unix 시각을 30으로 나눈 값과 일치하는지 비교하면 된다(30초 안에서는 같은 값이 유지됨을 관찰할 수 있다).

## 잘못 알고 있던 것

- **"HMAC 결과를 그냥 앞 몇 바이트 잘라서 숫자로 바꾼다."** — 아니다. 자르는 시작 위치(offset)가 고정이 아니라 HMAC 출력 마지막 바이트의 하위 4비트로 매번 다르게 결정된다(§5.3). 고정 위치 절단이라면 공격자가 그 위치만 노려 분석할 여지가 생기지만, 동적 절단에서는 그 위치조차 비밀키·카운터에 종속된다.
- **"OTP가 6자리인 건 그냥 화면에 표시하기 좋은 자릿수라서다."** — 자릿수(Digit)는 `mod 10^Digit`의 지수로, 코드 공간 크기(6자리=100만 가지)를 직접 결정하는 보안 파라미터다. 자릿수를 줄이면 무차별 대입에 필요한 시도 횟수도 그만큼 줄어든다.
- **"시간 창(윈도우)을 넉넉히 잡아두면 UX만 좋아지고 손해는 없다."** — RFC 6238 §5.2는 창을 넓힐수록 한 번의 코드로 유효한 시간 구간이 늘어나 브루트포스 공격 표면이 커진다고 명시한다. 창 크기는 순수 UX 파라미터가 아니라 보안-사용성 트레이드오프다.
- **"서버는 클라이언트가 시도할 때마다 카운터를 맞춰나간다(HOTP)."** — §7.2는 검증에 **성공했을 때만** 서버 카운터를 전진시키도록 규정한다. 실패한 시도로 카운터가 움직이면 정상 클라이언트와의 동기화가 오히려 깨질 수 있다.

## 더 파고들 만한 것

- WebAuthn/FIDO2의 challenge-response 방식이 OTP류(HOTP/TOTP) 대비 피싱에 왜 근본적으로 더 강한지 — 공유 비밀 vs 공개키 서명의 차이.
- U2F/FIDO 하드웨어 토큰이 쓰는 카운터 기반 replay 방지가 HOTP의 이벤트 카운터와 어떤 점에서 같고 다른지.
